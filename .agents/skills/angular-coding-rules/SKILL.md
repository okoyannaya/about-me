# Правила написания кода проекта

Применяй этот скилл при каждом создании или изменении кода в этом репозитории. Соблюдай все 46 правил ниже в применимой к задаче части непосредственно во время написания кода, а не только при итоговом ревью. Для задач без написания кода скилл не требует изменений файлов.

## Порядок работы

- Перед первым изменением прочитай этот файл полностью, применимые `AGENTS.md`, соседний код, `package.json`, lock-файл и относящиеся к задаче настройки TypeScript/Angular. Определи фактические версии и доступные команды проверок.
- Учитывай пользовательские изменения в рабочем дереве. Применяй правила к создаваемому и изменяемому коду; удаляй потерявшие назначение части затронутой логики. Не расширяй задачу до несвязанной миграции всего проекта.
- Используй API, поддерживаемые установленной версией. На момент создания скилла проект использует Angular 21; перед каждой задачей проверяй актуальную версию. Условия для Angular 22+ не означают, что проект уже обновлён.
- Именование Observable/signals, строковые enum, русский язык тест-кейсов и запрет геттеров в шаблонах — обязательные соглашения проекта. Сохраняй их и при использовании сторонних примеров кода.
- Перед завершением проверь изменённый код по всем применимым правилам, выполни доступные проверки, соответствующие изменению, и исправь обнаруженные нарушения. В отчёте укажи фактически выполненные проверки и оставшиеся ограничения.

## Принципы организации и поддержки кода

1. **KISS — сохраняй простоту.** Выбирай понятное решение с минимально необходимым количеством условий, сущностей и уровней абстракции. Усложняй код только под конкретную потребность.

2. **DRY — не дублируй знания и логику.** Выноси общие бизнес-правила и повторяющиеся операции в переиспользуемые функции, компоненты или сервисы. Объединяй код, когда у него общий смысл и причины изменения.

3. **SOLID: S — одна ответственность.** Разделяй код, который меняется по разным причинам. Компонент отвечает за представление; независимые бизнес-правила и работу с данными размещай отдельно.

4. **SOLID: O — возможность расширения.** В местах с несколькими вариантами поведения используй композицию, стратегии или конфигурацию, позволяющие добавлять варианты с минимальными изменениями существующей логики.

5. **SOLID: L — соблюдение контракта.** Реализации одного контракта должны быть взаимозаменяемыми и сохранять ожидаемое поведение: допустимые входы, результаты и обработку ошибок.

6. **SOLID: I — небольшие интерфейсы.** Создавай интерфейсы под конкретные задачи потребителей. Компонент или сервис должен зависеть только от необходимых ему возможностей.

7. **SOLID: D — зависимости от контрактов.** Отделяй бизнес-логику от деталей реализации. Подставляй зависимости через DI; при необходимости используй контракт и `InjectionToken`. Абстракции должны решать реальную задачу.

8. **Удаляй код, который больше не используется.** Убирай ненужные методы, поля, импорты, ветки, файлы, зависимости и закомментированные реализации. Перед удалением проверяй обращения из шаблонов, маршрутов, DI и публичного API. Не оставляй заменённую реализацию «на всякий случай».

9. **Группируй код по функциональности.** Держи компоненты, сервисы и тесты одной возможности рядом, например в `features/profile/`. Давай вспомогательным файлам конкретные названия.

## Именование

10. **Переменные, свойства и методы — `camelCase`.** Используй смысловые имена: `userName`, `selectedItems`, `saveProfile`. Избегай префиксов типов `strName`, `boolActive` и непонятных сокращений.

11. **Булевы значения — с понятным префиксом.** Начинай имена с `is`, `has`, `can`, `should`: `isLoading`, `hasError`, `canSubmit`, `shouldRefresh`. Избегай двойных отрицаний.

12. **Observable — с суффиксом `$`.** Называй потоки `users$`, `searchQuery$`, `isLoading$`. Суффикс `$` обозначает Observable; применяй это соглашение последовательно.

13. **Signals — без специального суффикса.** Используй `count`, `user`, `isLoading`; читай через `count()`. Придерживайся единого стиля без `_`, `$` и `Signal` для обозначения сигнала.

14. **Классы, интерфейсы, типы и enum — `PascalCase`.** Например, `UserCard`, `UserProfile`, `ThemeMode`. Суффиксы вроде `Component` применяй согласно принятому стилю проекта.

15. **Inputs и outputs — по смыслу данных и событий.** Входы: `user`, `isDisabled`; события: `saved`, `userSaved`, `selectionChange`. Не добавляй `input`/`output` в имя; избегай префикса `on` у outputs и совпадений с DOM-событиями.

16. **Методы и обработчики — по выполняемому действию.** Используй `saveProfile()`, `selectUser()`, `closeDialog()`. Имя должно объяснять результат вызова.

17. **Шаблонные переменные — `camelCase`.** Имя отражает назначение элемента или значения: `#emailInput`, `@let currentUser = user();`.

18. **Селекторы — с префиксом проекта и подходящим регистром.** Для элементов компонентов используй `kebab-case`, например `app-user-card`; для атрибутных директив — `camelCase`, например `[appTooltip]`. Учитывай префикс текущего проекта.

19. **Файлы — `kebab-case` и общее базовое имя.** Например, `user-profile.ts`, `user-profile.html`, `user-profile.scss`, `user-profile.spec.ts`. Поддерживай существующее соглашение о суффиксах.

20. **Повторяющиеся строковые варианты — в строковые `enum`.** Режимы, статусы и варианты определяй централизованно. В логике, компонентах и тестах используй `ThemeMode.Dark`; строку `'dark'` задавай внутри enum.

## TypeScript и компоненты

21. **Используй строгую типизацию.** Включай `strict: true` и `strictTemplates: true`. Устраняй причины ошибок типов, избегая необоснованных `$any()`, приведения `as` и оператора `!`. Не ослабляй существующие проверки ради прохождения сборки.

22. **Избегай `any` и лишних аннотаций.** Для неизвестных данных используй `unknown` с проверкой. Очевидные типы позволяй выводить TypeScript: `const count = 0`.

23. **Используй `readonly` для непереназначаемых полей.** Помечай функциональные inputs, outputs, models, queries и другие стабильные ссылки как `readonly`. Это не делает вложенные объекты неизменяемыми; значение writable signal по-прежнему можно обновлять через его API.

24. **Ограничивай доступ к деталям реализации.** `private` — для внутренней логики; `protected` — для членов, необходимых только шаблону; публичными оставляй API компонента.

25. **Соблюдай порядок членов класса.** Зависимости, inputs, outputs, queries и остальные поля размещай перед методами. Используй одинаковый порядок в проекте.

26. **Используй standalone-компоненты в новом коде.** Подключай необходимые компоненты, директивы и pipes через `imports`. Импортируй только используемые зависимости.

27. **Явно описывай API компонента.** Используй `input()`, `input.required<T>()`, `output<T>()`. Для намеренной двусторонней привязки применяй `model()`.

28. **Предпочитай `inject()` для зависимостей.** Например, `private readonly users = inject(UserStore)`. Обычно вызывай при инициализации поля; обычный `ngOnInit` не предоставляет контекст DI.

29. **Разделяй исходное и вычисляемое состояние.** Локальное реактивное состояние храни в `signal()`, зависимые значения вычисляй через `computed()`. Не поддерживай вручную копии вычисляемых данных.

30. **Используй `effect()` для побочных действий.** Применяй для синхронизации с хранилищем, аналитикой или сторонними API. Производные значения описывай через `computed()`.

31. **Обновляй реактивные объекты без прямой мутации.** Создавай новую ссылку: `items.update(items => [...items, newItem])`. При необходимости предоставляй внешним потребителям сигнал через `asReadonly()`.

## Шаблоны, асинхронная работа и качество

32. **Используй современный control flow.** В новом коде применяй `@if`, `@for`, `@switch`. Синтаксис доступен начиная с Angular 17.

33. **Задавай стабильный ключ в `@for`.** Используй `track user.id`. `$index` подходит для статичных списков, состав и порядок которых не меняются.

34. **Оставляй шаблоны простыми.** Сложные вычисления переноси в TypeScript, обычно в `computed()`. Простые выражения и чтение signals оставляй в шаблоне.

35. **Никогда не используй TypeScript-геттеры в шаблонах.** Не обращайся из inline- и внешних шаблонов к свойствам, объявленным через `get`, например `public get totalChannel()`, даже если геттер простой. Это относится ко всем выражениям шаблона: интерполяциям, bindings, control flow и обработчикам. Используй `computed()` для значений, зависящих от signals, либо явно обновляемое поле. Чтение сигнала `totalChannel()` разрешено. Не заменяй геттер обычным методом в шаблоне только ради обхода правила. Помни, что `computed()` не отслеживает изменения обычных полей.

36. **Предпочитай прямые привязки классов и стилей.** Например, `[class.active]="isActive()"`, `[style.width.px]="width()"`. При замене `ngClass` учитывай различия обработки объектов и мутаций.

37. **Описывай host-привязки через `host`.** Классы, атрибуты и обработчики host-элемента размещай в `@Component({ host: { ... } })` или `@Directive`.

38. **Настраивай `OnPush` с учётом версии Angular.** В Angular 22+ это стратегия по умолчанию. В более ранних версиях задавай явно там, где используется соответствующая модель обновления состояния. Для текущего Angular 21 не полагайся на значение по умолчанию из Angular 22.

39. **Подключай Observable к представлению через `async` или `toSignal()`.** Используй `async` в шаблоне, `toSignal()` — для получения сигнала. Результат `toSignal()` переиспользуй, чтобы не создавать повторные подписки.

40. **Управляй временем жизни ручных подписок.** Применяй `takeUntilDestroyed()`. Вне контекста DI передавай заранее полученный `DestroyRef`.

41. **Объединяй асинхронные операции через RxJS.** Избегай вложенных `subscribe`. Выбирай оператор по задаче: `switchMap` — переключение на новый поток, `concatMap` — последовательность, `mergeMap` — параллельная работа.

42. **Используй типизированные формы.** В Reactive Forms применяй типизированные controls и осознанно выбирай `nonNullable`. Для новых форм в Angular 22+ рассматривай стабильные Signal Forms. Не переноси предположение об их стабильности на Angular 21; учитывай установленную версию и существующий подход проекта.

43. **Соблюдай семантику HTML и доступность.** Действия оформляй через `<button>`, переходы — через `<a>`. Обеспечивай подписи полей, доступные имена, управление клавиатурой и видимый фокус.

44. **Проверяй поведение тестами.** Проверяй отображение данных, реакцию на ввод и события компонента. В тестах шаблонов моделируй пользовательские действия и дожидайся обновления представления.

45. **Пиши названия тест-кейсов на русском.** В `it`, `test`, `it.each`, `test.each` описывай проверяемое поведение: `сохраняет выбранную тему после обновления страницы`.

46. **Автоматизируй проверку качества.** Используй Prettier для форматирования, Angular ESLint для TypeScript и шаблонов. Запускай линтер, проверку форматирования, сборку и необходимые тесты в CI. Перед запуском проверь существующие scripts и конфигурацию; при отсутствии проверки явно укажи это. Настраивай отсутствующие инструменты при работе над tooling/CI, не подменяя этим текущую задачу.
